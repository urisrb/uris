title: Resources
description: A place uris reads from, writes to, or asks something of.

A resource is one instance of a type — a bucket, a directory, a mailbox, an inference endpoint, an
MCP server — keyed uniquely within its tenant and type. What each type needs and what it can do is
listed in [the resource reference](/reference/resources/); this page is what they all share.

## What a type declares

A type states what it is with three class macros, and nothing else decides it:

| | |
| --- | --- |
| `serves` | capabilities — `storage`, `inference`, `browser`, `search`, `tools`, `integration` |
| `accepts` | mime patterns it will hold, such as `*/*` |
| `up_to` | the largest file it will take, in bytes, or nothing for no limit |

Every save copies the declaration into the `serving` jsonb column, so "which active stores accept a
4GB video" is a SQL query rather than loading every resource into Ruby to ask it. A copy is only as
fresh as its last save, so `bin/rails uris:resources`, which the production entrypoint runs before
the server starts, restates every row inside every tenant before it reconciles declarations.

A tenant has at most one default storage and one default inference resource, and only a resource
that serves the capability can hold it. Making one the default clears the flag on the other.
Snapshots from the web go to default storage unless told otherwise, an upload nobody placed lands
there, and inference prefers the default when more than one resource could answer a role.

## Where they come from

`config/resources.yml` is ERB, keyed by environment, with every host and secret read from the
environment. The shipped file declares a `files` filesystem resource as default storage.
`Resource.declare!` reconciles it per tenant: it creates or updates each declared key and never
deletes, so a resource dropped from the file is left standing rather than removed from under
whoever is using it.

The browser attaches the rest. A type that can be attached returns an `attaching` description — a
label and a list of fields — and the form is rendered from it. `Resource::Settings` reads the given
values against those fields for both the file and the form: anything the type does not declare is
dropped, a missing required field is refused, and each value lands in `details` or, when the field
is a secret, in `credentials`. Credentials are encrypted at rest, and the audit trail records which
fields were set, never their values. Attaching runs a first check and reports what it said.

A resource is changed through the same form. Its type and key stay as they were; its name and
fields are read against the type again, a secret left empty keeps what it held, and a field the
new answers no longer ask for is dropped with its value. What the form reads back is only what
is held in the clear, and the names of the encrypted fields that hold something. The change is
checked and audited the way attaching is.

A filesystem resource is only attachable when `URIS_FILESYSTEM_ROOTS` names directories. Each
tenant is given its own directory under every one of them, named for its subdomain and made on
first use, and a resource's root has to sit inside one of those — the root itself is shared by
every tenant on the server, so it is never a place one can reach. A relative root is taken from the
tenant's directory under the first root, which is where the shipped `files` resource, root `.`,
lives. A root is checked where it really points, so a symlink out of the tenant's directory is
refused, and a write never follows one.

## Resources connected through masks

Google Drive, OneDrive, and an MCP server whose authentication is `masks` use somebody's own
account. Nobody types a secret into uris.

1. **Attach** it. It starts out not connected.
2. **Connect** it. The browser goes to masks, which asks the person's consent and signs them in to
   the provider if it has to, then comes back.
3. It **syncs and answers** from then on, with nobody signed in.
4. If the person stops uris using the account in masks, the resource shows **Reconnect** and its
   syncs stop until somebody does.

masks keeps the provider's tokens; uris keeps a [delegation](https://masks.pages.dev/concepts/delegation/)
— the connection and a secret, encrypted in the resource's credentials — and trades the secret for
a provider token when the last one runs out.

What uris enforces:

- `/resources/<id>/connect` needs `uris:resources:command`, and the resource has to be one the
  caller can see.
- `/connect/callback` refuses a `state` this browser did not start, a callback somebody else
  finished, and a connection masks made for a different person.
- One worker at a time renews a resource's token, under a row lock, because a secret spent twice is
  revoked. Every rotated secret is kept.
- A provider API that refuses the token gets one fresh token and one more try.
- masks refusing marks `needs_connect_at` and raises `Resource::Unusable`, which stops a sync
  instead of retrying it. masks not answering is `Resource::Failed`, retried as usual. A check or
  sync that succeeds clears the mark.

## Only mine, or everyone's

Whoever attaches a resource says who can use it. **Everyone here** is the default, and what every
resource was before. **Only me** records the attaching person's subject as `owner_subject`, and from
then on the resource is absent for anybody else — from the resources query and every mutation that
names one, from the `resource` and `feeds` tools, from the connect route, and from the MCP tools a
personal server offers, which only its owner sees. A type connected through masks starts as only
the attaching person's.

What a personal resource syncs is catalogued like anything else, for the whole tenant. A personal
resource is never where everybody's drops or questions go, and an agent working on a feed reaches
only the resources everyone here can.

## Syncing

A type that implements `each_page` can sync; one that does not, like the browser, can neither sync
nor keep a schedule. `sync_interval` is at least a minute, and `ScheduleSyncsJob` looks every minute
for resources that are due.

Starting a sync claims the resource with a single conditional update, so two workers cannot both
start one, and opens a run of kind `sync`. The job walks pages with job-iteration, recording a
[reference](/concepts/references/) for each object and analyzing any [feed](/concepts/feeds/) not
yet analyzed, and resumes at its cursor after a deploy. A `Resource::Failed` gets five attempts
before the run fails. Finishing clears the claim and sets the next sync on the original
cadence, skipping slots that were missed. A sync that fails clears the claim too, without recording
the resource as synced. One whose worker died holds its claim for six hours, after which it counts as
abandoned and another may start.

A run can be cancelled, and stops when it passes its deadline.

## Reaching through another resource

`via` points a resource at a transport — a resource that serves `transport` and answers `reach!` —
and an OpenAI-compatible endpoint dials its base URL through it instead of directly. Validation refuses a `via` that does
not serve `transport`, belongs to another tenant, points at itself, loops, or sits more than four
hops from anything that answers. The foreign key is composite — `(via_id, tenant_id)` references
`(id, tenant_id)` — so the database itself cannot join a resource to another tenant's transport,
whatever the application does. A transport cannot be archived while an active resource is reached
through it.

## Health, internal stores and archiving

A check calls the type's `check!` and records `checked_at` and `check_error`; a resource is healthy
when it has been checked and the last check raised nothing. `ScheduleChecksJob` looks every hour for
resources never checked or not checked in six hours, and checks each in a job of its own, so a
resource that stopped answering shows it before a sync or a tool call meets it. One that is syncing
is skipped, since the sync is the better test. Checking an MCP server asks it again what tools it
offers, so what it adds or drops reaches the proxy within the same six hours.

uris keeps two stores for itself: `children`, for what is extracted from a file, and `derived`, for
previews and thumbnails. They are database resources, and they are never offered as a place to put
an upload. Neither is listed or reachable by key through GraphQL or MCP, and neither can be archived,
synced, scheduled or made a default, since uris writes into them whatever anyone sets.

Archiving sets `archived_at` and deletes nothing. An archived resource drops out of capability
queries, placement, the defaults and the sync schedule, and restoring it clears the timestamp.
