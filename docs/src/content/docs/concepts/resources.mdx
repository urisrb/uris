A resource is a place items live. It is an *instance* — one bucket, one mailbox — and its type is
the STI subclass it belongs to.

`app/models/resource.rb`, `app/models/resource/`

Identity is `(tenant_id, type, key)`; `key` is validated unique within that pair. `sti_name`
dasherizes the class name, so `Resource::OauthGoogle` stores and reports as `oauth-google`.

`Caldav` and `Carddav` subclass `Webdav` and inherit its `each_page`, narrowing what they walk with
a `wanted?` predicate.

`Resource::Api` is the same idea one layer up, and not a type either: `github`, `notion`, `slack`
and `microsoft-graph` are all a bearer token, a JSON body and a cursor, so the dialling, the
byte cap, the 401 that is worth releasing a token for and the 429 that is worth retrying live in
one place. What a subclass writes is where its pages come from and what a record looks like
flattened into text.

`Resource::Brokered` is a concern, not a type. `oauth-google` and `microsoft-graph` include it —
see [Enrollment](#enrollment) below.

### Records rather than files

`github`, `notion` and `slack` catalogue things that were never files. There is no byte to point
at, so `download` composes one: an issue becomes its title, its body and its discussion; a Notion
page becomes its blocks flattened to markdown; a Slack thread becomes its replies with names rather
than user ids. All three land as `text`, which is what makes them searchable next to a PDF.

Their version is the part that moves. A GitHub issue's is `updated_at`, a Notion page's is
`last_edited_time`, and a Slack thread's is its reply count and latest reply together — because a
thread grows after it is written, and a new reply has to be a new version or the item is never read
again.

One class serves every vendor speaking its dialect: `s3` covers AWS, R2, B2, Wasabi, MinIO and
Garage.

## Capability

`self.capabilities` returns an array of symbols. `storage`, `integration`, `inference` and
`browser` are in use; `transport` is defined and unimplemented.

Only `storage` and `inference` are defaultable — `DEFAULTABLE` maps those two onto their columns,
so a tenant can name the one bucket exports land in and the one backend summaries run through.
`browser` has no default column because there is nothing to choose between: a `web` resource
renders through the browser on the machine running the worker.

## Reaching a resource

`via_id` is a nullable self-reference: *this resource is reached through that one*. Null means
reached directly. A resource named as `via` must declare the `transport` capability and implement
`reach!(url)`, which rewrites the URL its dependent would otherwise dial.

The edge is validated both ways. A `via` must be this tenant's, must not be the resource itself,
must not close a loop, and must not sit more than `MAX_HOPS` away. A transport that something still
rides on cannot be archived, and the database refuses to delete it or to point a `via` at another
tenant — the foreign key carries `tenant_id`, so a cross-tenant transport is unrepresentable rather
than merely refused.

`storage?` gates two items: being an export destination (`Resource#storage!`) and being the
tenant's `default_storage`, which `Resource#make_default_storage!` sets exclusively.

## Syncable

`Resource#syncable?` is `respond_to?(:each_page)`. There is no flag and no registry — a type either
implements the enumerator or it cannot sync.

Only a syncable resource may hold a `sync_interval`, enforced by the
`only_a_syncable_resource_keeps_a_schedule` validation.

| | |
| --- | --- |
| `MINIMUM_SYNC_INTERVAL` | 1 minute |
| `SYNC_ABANDONED_AFTER` | 6 hours — after which `sync_started_at` no longer counts as a lock |

`claim_sync!` takes the lock with a conditional `UPDATE`, so a resource already syncing is left
alone rather than started twice. `release_sync!` clears it and computes `next_sync_at`.

## Commands

`self.command_schema` maps a command name to its parameter types; `?` marks a parameter optional.
`Resource#command` validates arguments against the schema and dispatches to `command_<name>`.

```ruby
# app/models/resource/s3.rb
{
  list: { prefix: "string?", continuation_token: "string?" },
  get:  { key: "string", version_id: "string?" },
  put:  { key: "string", body: "bytes" }
}
```

`describe_resource` returns this schema, so a caller discovers a type's vocabulary rather than
having it written down. See [MCP tools](/reference/tools/).

## Checking

`check!` is implemented per type and is cheap — a `HEAD` rather than a listing. `check` wraps it,
writes `checked_at` and `check_error`, and returns a boolean. `healthy?` reads those columns.

## Failure

Adapters raise `Resource::Failed` (or a subclass — `Resource::Filesystem::Escaped`,
`Resource::Rss::Gone`) rather than a vendor error. Jobs retry it with backoff; see
[Jobs](/concepts/jobs/).

## Attaching

`self.attaching` declares what a type needs before it can answer — a label, a blurb, what its `key`
means, and one entry per field. It sits beside `command_schema`, and for the same reason: a caller
discovers a type's vocabulary rather than having it written down somewhere that falls out of step.

```ruby
# app/models/resource/imap.rb
{
  label: "A mailbox",
  names: "A name for it",
  fields: [
    field("host", "Server", required: true, placeholder: "imap.example.com"),
    field("ssl", "Over TLS", kind: "boolean", value: "true"),
    field("username", "Username", required: true, held: :credentials),
    field("password", "Password", required: true, secret: true)
  ]
}
```

`held` says where a value is stored — `:details` or `:credentials`, the encrypted column. `secret`
only decides masking, so a username lives in `credentials` without being hidden from the person
typing it. Returning `nil` from `attaching` means a type nobody attaches by hand.

`Resource.attachable` walks `Resource::TYPES` and keeps the ones that answer. The `resourceTypes`
query serves them and `attachResource` consumes them:

- Only declared fields are read, so a key the form never offered cannot reach `details` or
  `credentials`.
- A dotted name nests — `models.fast` becomes `details["models"]["fast"]`.
- Nothing hands a credential back. The schema carries names and defaults, never values, and the
  audit event records which fields were set rather than what was typed into them.
- `database` is not attachable. `filesystem` is only offered where `URIS_FILESYSTEM_ROOTS` is set,
  since otherwise the form is a way to read any path on the host.
- Attaching runs `check` and reports what it said, so a bucket that does not answer looks wrong
  immediately rather than at the first sync.

A brokered type declares `attaching` with no fields and goes through `enrollResource` instead.

## Enrollment

Types that include `Resource::Brokered` hold a connection id, not a credential. `Broker.release`
exchanges it for an access token at the issuer's `/connections/token` endpoint on each use.

`Enrollment.open!` builds a signed, 30-minute (`Enrollment::WINDOW`) token; `/enroll/:token` is
where the browser completes it. Nothing is created until the link is followed.

Credentials never travel through an MCP tool call.

The provider a brokered type names — `google` for `oauth-google`, `microsoft` for
`microsoft-graph` — is a row in masks, not code in either repo. A provider there carries its own
authorization and token URLs, client id and secret, and scopes, so adding one is an administrative
act: for OneDrive, Microsoft's `/oauth2/v2.0/authorize` and `/oauth2/v2.0/token`, with
`Files.Read.All offline_access`. Nothing in uris knows the host, which is the
[boundary rule](/reference/configuration/) doing its job.

The other three API types take a token typed into the attach form instead, because that is the
credential their services issue: a GitHub personal access token, a Notion internal integration
secret, a Slack bot token. They are stored encrypted like any other credential and never leave the
server.
