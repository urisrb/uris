---
title: References
description: Where a feed's bytes live, how change is noticed, and what uris will delete.
---

A feed does not hold bytes. A reference points at them: a row that names a
[resource](/concepts/resources/) and where inside it the bytes are. A feed can have several
references — the same file in a bucket and in its export — and the catalog is what they have in
common.

## Roles

| Role | What it points at |
| --- | --- |
| `original` | the thing itself, wherever it was synced from or placed |
| `preview` | a large JPEG render, 1024 pixels wide, which the image analyzer reads rather than rendering again |
| `thumbnail` | a 320-pixel JPEG for the catalog |

`preview` and `thumbnail` are derived. A pass renders both once, for images, video, PDFs and
captured pages, and records them in the internal `derived` store, keyed `<feed id>/<role>.jpg`.
That store and the `children` store are `Resource::INTERNAL`: the app keeps them for itself and
never offers them as a place to put a file. Serving a thumbnail is reading the thumbnail
reference's bytes, so it passes the same grant check as any other bytes.

Everything that counts a feed's places — `Feed#reference`, the search document, `splitReference`,
`forgetFeed` — counts originals only.

## Locators

`locator` is a JSON object in whatever shape the resource needs to find the bytes again — a bucket
and a key, a path, a mailbox uid. `locator_key` is its stable string form, the path a person would
recognise. A `locator_key` is unique within a resource, in the model and in a partial unique
index on `(tenant, resource, locator_key)`, so one object in one place is one reference, and
syncing it again finds that reference rather than making a second.

## Noticing change

`version` is what the resource says identifies this revision of the bytes: an S3 or WebDAV etag,
a git sha, a Notion `last_edited_time`, a web capture's digest. When a sync reports a version that
differs from the one held, the reference sets `changed_at` and clears `analyzed_at`, and the sync
opens a new pass. A cached analysis step finished before `changed_at` is superseded rather than
reused, so a pass never describes bytes that are gone.

`source_version` belongs to a copy. When an export writes a feed into another resource, the new
reference records the version of the original it was copied from. The next export compares the
two and copies again only when the original has moved on.

## Moving between feeds

`move_to!` hands a reference to another feed. If that feed already holds the same place, the
reference is destroyed instead of duplicated. Either way, a `uris:file` feed left with no originals
is destroyed. `split!` is `move_to!` into a new feed with the same type, key and title, and
`splitReference` refuses a feed that has only one original. Sync and export are what move
references in practice.

## What uris deletes

Forgetting a feed destroys the row, its references, analyses, schedule, edges and extracted
children, and reports how many originals it stopped pointing at. It does not reach into the
resources those originals live in: the files stay exactly where they were.

The exception is bytes uris made itself. A reference in an internal store — a `preview` or
`thumbnail` render, or a child extracted from a message — deletes its blob when it is destroyed,
since nothing outside uris put it there. A file that was uploaded and never placed is purged with
its feed, since it was only ever staged.
