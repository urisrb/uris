`/mcp` is a Model Context Protocol endpoint over streamable HTTP. It takes the same masks access
token as the browser app — see [tenants](/concepts/tenants/) — and a request without one is answered
`401` with a `WWW-Authenticate` challenge naming
`/.well-known/oauth-protected-resource`. That document lists the resource URL, the masks issuer as
its authorization server, and every `uris:` scope with a description, which is what an OAuth-aware
client needs to find masks and ask for a token on its own.

Calls are rate-limited per token, or per address when there is none, at `URIS_MCP_LIMIT` a minute
(120 by default). An `Mcp-Session-Id` belongs to the subject that opened it and is refused to anyone
else.

## Four tools

| Tool | Scope to see it | What it is for |
| --- | --- | --- |
| `search` | `uris:catalog:read` | the whole catalog at once, or the newest feeds of a type |
| `feed` | `uris:catalog:read` | one [feed](/concepts/feeds/) in full; with `do`, note, rename, analyze, create or place it |
| `connect` | `uris:catalog:write` | join two feeds, or sever them |
| `resource` | `uris:resources:read` | list the [resources](/concepts/resources/), and ask one to run a command |

Inputs are generated into the [MCP reference](/reference/mcp/).

A token sees only the tools its scopes permit, and the `resource` tool is built per token by
`Tool::Resources.for`: `list`, `describe`, `check`, `runs`, `get`, `parameters` and `search` are
always in its schema, and `sync`, `export`, `cancel`, `put` and `snapshot` appear only when the token
carries `uris:resources:command`. A token with `uris:web:keep` also gets `snapshot`, which it can
send only to a resource that renders pages, the `web` type. An ungranted command is absent from `tools/list`, not refused when
called. Calls are still checked: `feed`'s writing verbs need `uris:catalog:write`, and searching a
search-capable resource needs `uris:web:read`. A token with `uris:mcp:call` also sees the tools of
any MCP server added as a resource, passed through.

## The agent

`Agent` runs a prompt against an inference resource that serves the `agent` role, offering it the
same four tools. It runs for a fixed number of turns — six by default, a feed's schedule can set
its own, never more than 32 — and each turn asks the model for a reply.

- A reply with no tool calls is the answer.
- Each tool call is checked against the tool's own input schema before it runs. An unknown tool,
  arguments that are not JSON, or arguments the schema refuses come back to the model as an error
  it can correct, rather than raising out of the loop.
- A tool result longer than 8,000 characters is cut, with a note saying how much was left off.
- Three failed calls in a row end the run as `flailed`. A call that succeeds resets the count.
- The last turn is offered no tools and told to answer from what it has already read.
- A run whose analysis is cancelled, or past its deadline, stops at the start of its next turn as
  `halted`.
- A run with an analysis is told how long it has, and offered `more_time`, which the loop answers
  itself rather than passing to a tool. Given minutes and a reason, it moves the deadline out, never
  past a day from the start. With under a minute left, the next turn is the last, so it answers from
  what it has instead of being cut off.

It returns an `Answer` holding what was said, why it stopped, the turns taken and every call made.

When a feed is analyzed, the agent is asked to file it — connect it to tags and related feeds, and
choose a resource for a file still waiting for one. An address feed with a schedule runs its own
prompt instead. See [analysis](/concepts/analysis/).

That agent is not acting as a person, so it does not borrow one's token. `Feed#grant` gives it a
grant of its own, subject `feed:` followed by the feed's key, holding `Feed::AGENT_SCOPES`:

```
uris:catalog:read  uris:catalog:write  uris:web:read  uris:resources:read
```

It can search, read, file and place, and ask resources read-only questions. It cannot sync, export
or write into a resource, reach an added MCP server, or touch settings.

## Asking

A question asked of the catalog is kept as a note and answered by an analysis with the cause `ask`.
`Asking` builds the prompts, and everything runs under the question's own grant, holding
`Feed::ASKING_SCOPES`:

```
uris:catalog:read  uris:catalog:write  uris:web:read  uris:web:keep  uris:resources:read
```

The question is answered by a lead and its scouts. The lead holds the question and the goal, and
its only tool is `scout`: it sends a task, such as finding what an address is and keeping its about
page, and gets back a short report. It never sees a raw search result or page, so its transcript
stays small however much is read. It may take 16 turns, bounded by its feed's timeout, and is turned
back once if it answers before sending a scout.

`Scouting` runs each task as an agent of its own, in a fresh context, with the real tools under the
same grant, for up to eight turns. Several scouts sent in one turn run side by side,
`URIS_SCOUTS_AT_ONCE` at a time (two by default), each in a thread that enters the tenant on its own
connection. A scout runs on the inference resource that declares the `scout` role, and on the
agent's model where none does. It is told how long it has, cannot ask for more, and stands down 90
seconds before the deadline so the lead still has time to answer. Its report is cut to 1,500
characters; the calls it made are kept for the judges and the connections.

Scouts are told only what the tenant has attached. With a search resource a scout can search the web.
With a fetch resource, such as `curl`, it can read a page. With a `web` resource it can keep a page as
a snapshot, which becomes an item of its own, and keeping the same address again later updates that
item. Without any of them the question is asked of the catalog alone.

A note that was asked is a conversation. `askCatalog` with the note's `feedId` asks a follow-up in
it, once the question before has been answered; the question is kept on the analysis that answers
it, and **Ask again** asks the latest one again. The lead of a follow-up is told the earlier questions
and their answers, up to eight of them with each answer cut to 1,500 characters, and told to read the
new question in their light without answering them again; its scouts are told which questions it
follows. When the reply lands, `Analyzer::Conversation` rolls the whole conversation into the
analysis — every question and answer as its text, and a summary, entities and keywords made from all
of it — so the note is searched and summarised as the conversation it has become rather than as its
first question.

The run is confined. `Current.confined_to` holds the feeds it made, and `feed`'s writing verbs
refuse any other feed, so a page telling the agent to rewrite a note or rename a file cannot. It
can create only notes, never a scheduled feed. `connect` needs one end to be the question or
something the run made. Snapshots are not confined: the page, not the agent, decides what one
holds.

A small model tends to stop early, so a scout's report is turned back, once for each shortfall, when:

- nothing came from the catalog and the web was never tried,
- the web was searched and no page was read, with the exact calls for the addresses the search
  returned,
- pages were read and none was kept, while something could keep them.

When the lead finishes, the question is connected to every feed its answer cites and every feed a
scout opened or made, and to every page a scout kept. Then ten judges on the `smart` model, or the
agent's model where no smart one is declared, each see the question, the lead's answer and only what
the scouts' tools returned. Each votes on whether the answer is supported by that evidence and whether what it kept is worth having again. The shares
are stored on the analysis as the `verified` step and exposed as `Analysis.verified` and
`Analysis.useful`. A judge that fails abstains. `ASK_VERIFICATIONS` sets how many judges there are.

## Budgets and gates

Starting work that can run long spends from a budget: `feed` with `do: analyze`, and `resource` with
`sync` or `export`. Each subject in a tenant may start `URIS_RUN_BUDGET` of them in a clock hour, 20
by default; `0` removes the ceiling. A feed's agent spends from its own subject's budget, not a
person's.

A gate is a row that stops a kind of job. The iterating jobs name theirs — `sync`, `analyze`,
`export` and `reindex` — and a gate can apply to the whole key or to one record, such as a single
resource for `sync`; the record's gate wins over the key's. A disabled gate marks the run gated and
does nothing; a gate that is enabled but not live lets `sync` and `reindex` walk and count without
writing. Gates are read again every 50 iterations, so closing one stops a run already under way.
`URIS_ITERATORS_DISABLED` closes every gate at once. Gates have no screen yet; they are set with
`Gate.set!` from a console.

## Audit

Every tool call writes an audit event: the tool, the scope, `ok`, `error` or `denied`, the subject and
client, the address and request id, and the duration. Arguments are summarized rather than stored —
strings cut to 200 characters, arrays counted, one level of nesting kept — and any key naming a
secret, password, token, credential, authorization or access key is replaced with `[redacted]`.
Refused authorizations, rate-limited calls, and some GraphQL mutations are recorded the same way.

Events are readable through the `auditEvents` query with `uris:catalog:read`. A daily job deletes
those older than `URIS_AUDIT_RETENTION_DAYS`, 90 by default; `0` keeps them forever.
